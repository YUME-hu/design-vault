# V2.3 技术方案：资产可编辑 + 合并动作

> 状态：**方案待确认，未动代码**。两个痛点：入库后的资产是死的、查重只有标记没有动作。

---

## 0. 先对齐一个事实

「合并」的后端**已经存在**（M3a 的 `mergePending` + `POST /api/pending/[id]/merge`），问题在前端与触发条件：

- 按钮只在 `duplicate_of` 存在时渲染；
- 你截图里 Claymorphism 的相似提示写在 `notes`（「发现相似风格：Glassmorphism」），但 `duplicate_of` 为 null，所以按钮不出现；
- 合并 API 也硬性要求 `duplicate_of`，没有「按名称解析目标」的能力。

所以 M9a 不是从零做合并，而是**补目标解析 + 补 UI 入口 + 补确认交互**。

## 1. M9a：合并到相似风格

### 1.1 目标解析（服务端，单一事实源）

新增纯函数（core 或 adapters）：

```ts
resolveMergeTarget(item, { styles, drafts }): { id, name, kind: "style"|"draft" } | null
```

顺序：

1. `item.duplicate_of` 命中 styles / drafts → 直接返回；
2. 否则从 `item.notes` 匹配 `发现相似风格：(.+?)(（|$)`，再按 `name` 精确匹配 styles / drafts；
3. 都找不到 → `null`（前端禁用按钮并说明原因）。

注意：`duplicate_of` 可能指向 pending（查重时 pending 也在候选池里），V2.3 **不支持合并到 pending**，返回 422 并提示「目标不是已入库资产」。

### 1.2 API

`POST /api/pending/[id]/merge` 扩展：

```jsonc
// 可选；不传则服务端按 1.1 解析
{ "targetId": "glassmorphism" }
```

服务端流程：

1. 找 pending，解析目标（显式 targetId 优先）；
2. 合并 `sources`（按 video + url + upstream 去重追加）；
3. 合并 `notes`：追加一段 `合并自 pending：<item.name> · <video/BV> · <item.notes>`，不覆盖原 notes；
4. 若目标 Style 有 `related_effects` 且 pending 带 `extracted_effects`，可顺带把 effect 关联上（M9a 先只做 sources + notes，避免范围膨胀）；
5. 写目标 JSON（原子写）→ 删除 pending → 返回 `{ ok, targetId, addedSources }`。

### 1.3 UI

- `/pending` 每条：若解析出目标，显示 **「合并到：<name>」** 按钮（即使没有 `duplicate_of`）；
- 点击后**内联二次确认**：`把 2 条来源合并到「Glassmorphism」？` → 确认 / 取消；
- 成功后行消失、toast/提示「已合并 N 条来源到 Glassmorphism」；
- 解析不到目标时按钮不渲染，或灰色提示「相似风格不在库中」。

## 2. M9b：资产编辑

### 2.1 先盘点现状

- **Styles 已有完整编辑页**：`/library/[id]/edit`（调色器 + 全字段表单 + `PUT /api/styles/[id]`）；
- **Effects / Components 没有编辑入口**，只能改 JSON。

所以 M9b 只补 effects / components，styles 只需要在详情页确认「编辑」入口存在（已有「编辑 · 打开调色器」）。

### 2.2 API 设计

不建议单一 `PUT /api/[entity]/[id]`（字段白名单容易漏、zod 报错模糊）。按实体拆：

```
PUT /api/components/[id]   { name?, category?, description?, framework?, code?, dependencies?, notes?, related_styles? }
PUT /api/effects/[id]      { name?, tech_stack?, description?, code_snippet?, performance_notes?, related_styles? }
```

服务端统一流程：

1. 读现有记录（找不到 404）；
2. 只接受白名单字段（zod `.strict()`，多余字段 400）；
3. `{ ...existing, ...patch, id 不变, updated_at: today }`；
4. 用完整 schema 校验（`componentSchema` / `effectSchema`）→ 失败 422 带 issues；
5. 原子写回 → `revalidatePath`。

并发说明：本地单用户，不做乐观锁；写入是 read-modify-write + rename，最后写者胜。

### 2.3 UI

**组件详情** `/components/[id]`：

- 右上角「编辑」→ 进入编辑态；
- 可编辑：`name / category(下拉) / framework(下拉) / description(textarea) / code(textarea, 等宽) / dependencies(逗号分隔) / related_styles(逗号分隔 id) / notes`；
- `states` V2.3 暂不编辑（结构复杂，等预览功能一起做）；
- 保存 → PUT → 退出编辑态并刷新；校验失败的 issues 显示在表单顶部。

**效果详情** `/effects`：

- 目前 effects 没有独立详情页，只有列表内联卡片；M9b 增加 `/effects/[id]` 详情页（或至少一个内联编辑弹层），字段：name / tech_stack / description / code_snippet / performance_notes / related_styles。

**风格详情** `/library/[id]`：

- 已有「编辑 · 打开调色器」，M9b 不改逻辑，只确认入口可见。
