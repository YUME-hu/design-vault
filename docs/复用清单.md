# 可复用项目调研（吃猪肉，不养猪）

> 目标：M0 之后少造轮子。这里的判断标准只有一条 —— **能不能直接替换掉计划书里某个"要自己写"的环节**。
> 说明：本机环境能打开 github.com 页面，但 `raw.githubusercontent.com` 解析失败，所以下表信息来自仓库描述与检索摘要，**没有逐个读源码**。真要用之前再核一遍 license 与实现。

## 结论先说

1. **没有现成的「B 站设计 UP 主 → 风格库」端到端项目**。你这套「信源 → 种子 → 色板 → 人工审核」的链路是自定义的，M2 仍要自己写。
2. 真正能省时间的是**零件**，而且是三块：
   - **调色板生成**（M1 调色器）→ dittoTones 的思路 + 现成算法
   - **配色审计**（M1 对比度）→ palettecore
   - **种子风格批量**（M0 补 4 条 / M1 冷启动）→ stylekit、awesome-design-md
3. M0 一个都不需要，所以 M0 目前是零依赖自写（只有字体/UI 原语这些常规包）。

## 不建议复用的

- **整站模板 / 大而全的设计系统**：本项目要的是「一条可复制的资产」，不是再装一套组件库。多引一层抽象，M1 的调色器反而更难写。
- **自动抓取 + 自动入库的一体化爬虫**：和「强制 pending 人工审核」的核心原则冲突。抓取要自己掌握节奏与白名单。
- **别人写好的风格描述文案**：风格库的价值在"你认可的审美判断"，抄文案等于把库变成二手摘要。

## 下一步的最小采购顺序

1. **M1 前**：读 dittoTones 的色阶推导（决定调色器算法），Radix Colors 定为主色板。
2. **M1 中**：对比度检测自己写（WCAG 相对亮度公式），不引 Python。
3. **M0 补种子时**：先看 stylekit 的条目结构，再决定 `components` 字段是否要再拆一层（现在是一个 `key → 一句话规格` 的 map）。
4. **M2 前**：bilibili-api-python 跑通"只读收藏夹 + 取字幕"两件事，再决定要不要 ASR 兜底。

## 顺带发现

- `uisdc` 那两篇文章里的"68 个品牌规范""58 个网站 UI 规范"是同一批内容的两种转述，说明这类"品牌规范转 markdown"的资源正在被批量生产 —— 对你有利，但会让**去重与提炼**变成 M2 之后的主要成本，而不是抓取。
- 检索中还出现过 `@zakkster/lite-hueforge`、`palettecore` 这类 npm/pypi 小包。前者标了 ⚠️，不建议；后者是 Python，只作为算法参考。
